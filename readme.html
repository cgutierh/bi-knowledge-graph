1 · Interfaz web (BI_KG_web.zip)

Es una aplicación estática que no necesita backend. La búsqueda, las fichas de nodo y el vecindario funcionan con data/kg.json. Las consultas SPARQL usan Oxigraph (WebAssembly), que se ejecuta en el navegador sobre data/kg.trig y data/ontology.ttl.

Contenido de la carpeta

ArchivoQué es

Probarla en tu ordenador

Tiene que servirse por HTTP: si abres index.html con doble clic, el navegador no deja cargar los datos.

cd bi-kg-web
python3 -m http.server 8000
# abre http://localhost:8000

Publicarla

  • Copia la carpeta bi-kg-web tal cual a cualquier hosting estático: Netlify, Vercel, GitHub Pages, S3 + CloudFront o un nginx interno.
  • El servidor tiene que entregar los .wasm como application/wasm. Los servidores habituales ya lo hacen.
  • Necesita conexión a internet para cargar d3 (cdnjs) y las tipografías (Google Fonts). Sin d3 no se dibuja el mapa de vecindario, pero el resto funciona; sin las tipografías se usan las del sistema.
Los datos van dentro de la carpeta y cualquiera que tenga la URL podrá verlos. Si el contenido es confidencial, publícala en un hosting con acceso restringido, como una intranet o un hosting con autenticación.

Cómo se usa

  • Buscar: texto libre; "frase exacta" entre comillas; o campo:valor para buscar un valor exacto en un campo, por ejemplo claim_status:approved, claim_status:candidate o key_message_type:efficacy. Puedes combinarlos: key_message_type:efficacy ckd.
  • Explorar: filtra por grafo y tipo. Pulsa un nodo para ver su procedencia, sus propiedades, su vecindario y sus relaciones. Todos los enlaces llevan a otros nodos.
  • SPARQL: elige una consulta preparada o escribe la tuya, y ejecútala con el botón o con Ctrl/Cmd + Enter. Todos los grafos se consultan como uno solo; para separar por marca usa GRAPH ?g { … }. Prefijo del vocabulario: PREFIX kg: <urn:kg:vocab:>.
  • Esquema: clases y relaciones con sus recuentos. Pulsa una clase para listar sus nodos.

Actualizar los datos

  1. Regenera el RDF con build.py del paquete de reconstrucción: python3 build.py <carpeta_export> <carpeta_salida>.
  2. Genera el JSON del explorador: python3 webdata.py <carpeta_export> data.
  3. Copia rdf/bi_kg_all.trig como data/kg.trig y ontology/bi_kg_ontology.ttl como data/ontology.ttl.

2 · Paquete de reconstrucción (BI_KG_reconstruido.zip)

Origen: BI_Knowledge_Graph_Export, exportado el 29-sep-2026. Contiene tres grafos de marca: boehringer-ingelheim («Life Forward»), jardiance y ofev, más 2 nodos compartidos de ámbito enterprise. En total, 4.912 nodos y 7.599 relaciones.

Decisiones de reconstrucción

  • Se mantienen las URN originales (urn:kg:vocab: para el vocabulario y urn:kg:<marca>:… para las instancias), así que todo sigue siendo compatible con el export.
  • Las aristas reificadas ({source, target}) se convierten en tripletas directas. Las aristas no tenían propiedades propias, así que no se pierde nada.
  • Se añaden 3 superclases: DomainEntity, que el export usaba sin declararla; ProvenanceEntity, subclase de prov:Entity; y ClinicalOutcome.
  • DERIVED_FROM_* son subpropiedades de prov:wasDerivedFrom, y las relaciones de contención lo son de dcterms:hasPart.
  • Si la definición de una clase varía entre marcas, la definición base va en skos:definition y las variantes en skos:scopeNote, marcadas con [marca].
  • Se añade un rdfs:label copiado de name, trial_name, module_name, sheet_name, nombre de archivo o section_title, para que los nodos sean legibles en las herramientas.

Validación

  • validate.py vuelve a leer Turtle, JSON-LD y GraphML y los compara con el original: mismos nodos y tipos, mismas aristas y mismos valores de propiedades, con 0 diferencias.
  • SHACL: Life Forward y OFEV cumplen. Jardiance tiene 112 violaciones: claims de eficacia sin CLAIM_REQUIRES_SAFETY, de los que 62 están aprobados.
